> Breach story 01 // July 2025

Tea app: the unlocked bucket

What happened

The women’s dating-safety app Tea leaked tens of thousands of user photos, including selfies and ID images.

Root cause

A cloud storage bucket was readable by anyone who found it. No hacking, just a URL.

Vibe lesson

Not proven to be vibe-coded, but exactly what AI scaffolds ship: defaults that work, not defaults that protect. Ask “who can read this?”

> Breach story 02 // 2025

Lovable apps: database door open

What happened

Researchers found 170+ apps built on Lovable exposing user data (CVE-2025-48757).

Root cause

Missing Row Level Security in Supabase. The public client key was fine; the missing database policy was not.

Vibe lesson

The UI hides data; only the database enforces access. If AI built your backend, read the policies yourself.

> Breach story 03 // July 2025

The agent that deleted prod

What happened

SaaStr’s Jason Lemkin reported that Replit’s AI agent wiped a live database during a code freeze, then misled him about it.

Root cause

An agent with write access to production. “Don’t touch it” was only text, not a permission.

Vibe lesson

Prompts are requests, not guardrails. Enforce limits with credentials, sandboxes and separate dev and prod.

> Lab 01 // the fix

Data must never become code

- db.query(`SELECT * FROM users WHERE id = ${id}`)
+ db.query('SELECT * FROM users WHERE id = $1', [id])
+ if (req.user.id !== id) return res.sendStatus(403)

Why it works

The database treats $1 as a value, never as SQL.

Ask your AI

“Rewrite every query as parameterized and add authorization checks.”

> Prompts // your first security control

Prompt like a defender: CORE

C

Context

Say what you’re building and that it’s your own code.

O

Outcome

Name the security goal: no secrets in code, authz on every route.

R

Rules

List constraints: parameterized queries, argon2, rate limits.

E

Evidence

Ask for the threats it considered and tests that prove it.

> Hands-on lab 07

Test your database in 60 seconds

$ curl "$URL/rest/v1/profiles?select=email" -H "apikey: $ANON"
[{"email":"a@x.com"},{"email":"b@y.com"},...]
# 😱 Public key + no RLS = everyone reads everyone.
$ psql -c "alter table profiles enable row level security;"
$ psql -c "create policy own on profiles for select using (auth.uid() = id);"
$ curl "$URL/rest/v1/profiles?select=email" -H "apikey: $ANON"
[]

Try it yourself

1. Grab your project URL and public key.

2. Run the first curl with only that key.

3. Got rows back? That’s a breach. Add RLS policies.

> Takeaways

Vibe responsibly

V

Verify

Read every diff. If you can’t explain it, don’t ship it.

I

Inspect

Vet dependencies. Run SAST and secret scanning in CI.

B

Bound

Least privilege, sandboxed agents, no prod credentials.

E

Enforce

Auth by default, tests, and CI gates that block bad merges.
